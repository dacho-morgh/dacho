# Company profile persistence and privacy — T05/T06

Date: 2026-10-24. Issues: [#19](https://github.com/dacho-morgh/dacho/issues/19), [#20](https://github.com/dacho-morgh/dacho/issues/20). Branch: `codex/company-profile-persistence-privacy`, base `staging`.

## Delivered behavior

The backend Payload company adapter now writes addresses and executives on creation and partial update. Omitted arrays remain untouched; explicit empty arrays clear them. Address row IDs survive reload/edit/delete. Only declared nested fields are forwarded. Numeric representative IDs are serialized as numbers for Payload's Postgres relationship validation.

The `companies` collection is private: current `admin` accounts can read/edit all companies; a current `representative` can read/edit only the company linked to that person. Anonymous visitors, content-only editors and unassigned reviewers cannot read the private collection. List/search/count and Local API calls with `overrideAccess: false` use the same scope. Representative relationships have `maxDepth: 0`, so REST dossier reads do not hydrate authentication records.

Public presentation uses `GET /api/companies/directory`, with an explicit response of `id`, `name`, `type`, `province`, `city` and pagination metadata. Only positive integer `page` is accepted as input; arbitrary private filters, sorting, selection and population are ignored. The endpoint intentionally reads through collection access internally and explicitly projects only those public fields. Existing consumers of unrestricted `/api/companies` must use this endpoint for public directory data.

Representatives cannot reassign the company's national ID or representative link. The dashboard renders national ID read-only and rejects a changed ID before applying any accompanying edits. Administrators retain correction authority. Normal company description/profile edits remain available. Identity re-verification and immutable approved snapshots belong to T14/T15; this change does not introduce verification status or claim to complete those workflows.

The privileged backend adapter now reloads current actor roles for profile and administrator company routes and resolves ownership from the stored representative relationship. Browser-supplied target-company/representative IDs cannot choose a different profile. Missing company records produce an error before acknowledging a write. The former user-store exception based only on `backend@dacho.local` email is removed; the seeded service account already holds `admin` authority.

Backend route tests cover target-ID injection, stale/forged role headers, protected identity edits and missing-company writes. An attempted GraphQL test exposed an existing schema construction failure: the Persian string values in `Companies.type` are invalid GraphQL enum names. No GraphQL request can currently complete through that schema. This batch does not change stored enum values or claim GraphQL end-to-end validation; collection access rules also govern GraphQL once the schema is repaired. Legal-type/knowledge-based classification restructuring remains T13 scope.

The seven-role migration, Secretariat/event assignment access and generalized authorization revocation remain T08/T09. This batch uses the existing role model without mapping every legacy admin to a new System Owner role. Private documents remain T10. No schema migration, production release or manual acceptance execution is included. UAT04/UAT05 and other human gates remain open until their complete prerequisites and human evidence exist.

## Stage-2 company dossier — T13

Date: 2026-10-26. Issue: [#27](https://github.com/dacho-morgh/dacho/issues/27). Branch: `codex/t13-company-dossier`, base `staging`.

The Payload `companies` collection now stores the stage-2 completion and resume fields: legal entity type, knowledge-based status, classification, founding year, activity domain, website, centre establishment, insured employee count, products/services, key members, past projects/customers, requested services, certificates/licences and an explicit absence list. Legal entity type and knowledge-based status are independent fields; neither is derived from the other. A cms-core migration (`20261026_120000_company_dossier`) adds the columns and the Payload child tables for each array. Existing registration identity remains managed by the earlier profile flow and is not re-asked by the dossier endpoints.

Migration ownership is split by schema, not by feature name. The cms-core migration owns every `public.companies` dossier column and child table, its `migrations/index.ts` registration and generated Payload types. The backend migration `1780511400009_company_dossier_backend.ts` is intentionally a no-op: the backend SQL path needs no new `dashboard` table or column, because dossier values live in Payload and missing-document checks read the existing `dashboard.private_documents` table and its `company_id` index. This keeps the backend sequence explicit without duplicating the CMS schema.

`GET /profile/dossier` returns the saved dossier, the company's available dossier documents and `missing`, which separates required gaps from optional value-or-absence questions. `PATCH /profile/dossier` writes only submitted fields (and any counterpart cleared or freed by an absence answer), so partial saves preserve the rest. Reads and writes for one representative are serialized while the merge is computed, which keeps coupled value/absence updates consistent. `PATCH /profile` also accepts top-level dossier fields, or the same fields nested under `dossier`, for clients that save the whole profile in one request; it validates the dossier before touching company, contact or executive data.

A representative can explicitly answer "does not have / not available" for centre establishment, website, insured employee count, past projects/customers, requested services, catalogues, certificates/licences and amendment notices. Declaring an item absent clears any conflicting value; submitting a value removes the absence answer. Declaring an item both absent and present in one write is rejected with `conflicting_absence`, and unknown absence keys are rejected with `invalid_absence_field`. The CMS collection applies the same allowed-key check to direct writes. Required fields (registration number, legal entity type, founding year, company status, classification, knowledge-based status, activity domain, products/services, addresses, articles of association and establishment notices) cannot be waived by the absence list; `foundingYear` must be a four-digit year between 1200 and 2100. Key members are stored but remain a proposed completion item, so an empty list does not block requesting verification. `canRequestVerification` becomes true only once no required gaps remain.

The absence list is a JSON field in Payload because it is a closed set of flags, not a repeatable row. The same value is used when deciding whether an optional item is still an open question, so the representative is not asked again after answering "does not have". Dossier document presence is read through the existing private-document repository rather than duplicating file metadata onto the company. This batch is backend/cms-core only; the dashboard UI, request submission and reviewer-facing dossier snapshots remain with their own tasks.

Validation for this batch: backend typecheck, backend unit tests (including Payload adapter regression coverage for every dossier array and the absence/conflict rules) and cms-core typecheck. No integration or E2E suite is claimed here.


## Frontend dossier editing and readiness — FE04/FE07/FE29/FE30 slice

The company and resume pages read and save the implemented T13 dossier contract, including repeatable items, private documents and all eight optional absence answers. Missing or failed dossier reads block editing rather than treating persisted information as an empty form. Saves are serialized in the browser; basic edits submit changed fields only and merge changed absence flags with a fresh read. Resume replacement slices reject a stale snapshot detected by a fresh read. This reduces lost updates but does not introduce a server-side optimistic concurrency token; truly concurrent writes from separate sessions still need that backend contract.

The readiness card refreshes after address and document changes. Completeness is not a verification state: no verification request has been sent by filling this form. Verification submission, pending/returned decisions, return reasons, resubmission and immutable approved snapshots remain T14/T15 dependencies. This slice does not complete full FE04 or UAT04–06. Figma parity and human acceptance remain unverified.
