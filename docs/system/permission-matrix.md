## Decision rules

One person has exactly one **operational** role: System Owner (O), Central Secretariat (S), Chief Reviewer (C), Reviewer (R), Employer Reviewer (E), Investment Reviewer (I), or Company Representative (P). `editor` is a separate CMS content privilege, not an operational workflow role; preserve existing editorial access during migration without making an editor a reviewer or owner. **Proposed technical mapping:** an account may retain editorial privilege alongside its one operational role, but operational authority must never be inferred from editorial privilege. Each existing `admin` account requires explicit review and mapping to the appropriate new role; do not automatically grant O to every legacy admin.

For the tables below, **own** means the representative's company, **assigned** means an active event/case/slot assignment for that person, **other** means a different company or event/case, and **unassigned** means an internal person with the named role but no current assignment to that case. A chief's event assignment covers that event's cases, not other events. A named employer is attached to one subtopic and its applicable cases. The investment reviewer is one assigned person per case, not an organization-wide voting group. O and S are Fund-wide where stated. Deny by default when role, ownership, active assignment, state or document category is missing. Historical assignment is audit visibility only, except explicitly authorized oversight.

The decision is made afresh on **every** CMS REST/GraphQL/Local API operation, backend route, dashboard proxy request, file URL, relationship population and read model. The proxy authenticates a Payload session and forwards identity with a shared secret; the backend must resolve current role/assignment/ownership itself rather than accept client-supplied IDs, role headers, recipient lists or target states as authority. Server-side field projections are mandatory. A page that hides a button is not an access check.

Additional field rules: C/R/E may receive only the company profile fields necessary to review their assigned proposal. They never inherit the private verification documents or financial fields from a populated company relationship. I receives the financial package only after an active case assignment and authorized handoff. P sees own submission/history and the published result, never internal scores, other reviewers' identities beyond a consciously approved progress view, deliberation or memo. A corrected proposal starts a new revision/round; old evaluations remain in restricted history and do not count toward current 4/4. Limiting chief/owner/Secretariat visibility of unfinished *answer content* to its author, while exposing only draft status/count, is a conservative technical projection pending any more specific Product decision; no unfinished evaluation contributes to 4/4.

## CMS, Local API, proxy and backend surfaces

| Surface | Required authorization and projection |
| --- | --- |
| Payload users and companies, direct REST/GraphQL and Local API | Restrict whole records and per-field reads/writes. P can modify only own company/user fields; identity/registration edits restart verification. S reads verification records; assigned case staff get a separate necessary-profile projection. O alone grants operational roles. Any Local API call acting for a user must set `overrideAccess: false` and pass the acting `req/user`, or use an explicitly reviewed service operation whose result is projected. |
| Payload editorial collections and public directory | Keep `editor` access to the documented content desk. Public `companies` responses use an explicit public-field whitelist, including nested/relationship fields. Event/exhibition public descriptions are separate from unpublished teams, applications and receipts. Editorial `media` remains public and cannot store private documents. |
| Dashboard same-origin proxy | Resolve current session on each request, strip browser-supplied identity/role/proxy-secret headers, forward only server-derived identity, and never expose the secret. Backend verifies secret plus actor identity and reloads current role/assignment/ownership. Proxy success alone grants no case permission. |
| Backend object/list/action endpoints | Enforce row scope and state at the query/action boundary; avoid confirming the existence of inaccessible object IDs. Returning 404 for such IDs is a proposed API convention to reconcile with the frontend/error contract, not an approved product status code. Counts, pagination totals, filters, search suggestions, exports, activity/history and queues use the identical row/field predicate as detail. An action's current revision/state is checked in the same transaction as its write. |
| Relationships/populated fields | Apply the viewer's field projection to every nested user, company, event, RFP, document and message record. Returning an authorized application with an unrestricted `owner`, `representative`, `reviewers` or `attachments` relation is forbidden. Use depth zero plus explicit authorized rehydration if generic population cannot enforce the projection. |
| Private file metadata and bytes | Store category, owner company, application/stage, revision, uploader and authorized audience. Authorize listing/metadata **and** download independently at request time. No public `/media` path, permanent signed URL, redirect, cache, thumbnail or filename may bypass current scope. Event financial-package metadata (category, filename, URL and package status) is confined to O/S/I with active assignment and authorized handoff/P own. Booth payment-receipt metadata, including amount/status, is confined to O/S/P owning that booth application; I has no booth-receipt access by virtue of an investment role. Apply the approved temporary [document policy](document-policy.json): Word/PDF only, 10 MB per file, multiple representations per field; images deferred. Upload policy does not broaden any audience. |

## Correspondence and revocation

| Actor | Send/receive scope | Attachment and case rule |
| --- | --- | --- |
| O | May message any user | Case attachment still checks the case and document audience; messaging does not create new dossier access. |
| S | Company support and authorized case correspondence | May request supplementary financial documents and deliver them only to the same authorized I/case. |
| C | May message any user | A message to an unassigned person does not reveal an unrelated case or its files. |
| R and E | Only the responsible C for their current assigned case | May attach only permitted case material; cannot read another reviewer's evaluation or financial documents through mail. |
| I | Authorized participants in their assigned case only | Memo to S; supplementary financial attachments keep financial audience. |
| P | Secretariat support only | Own support/case correspondence and own uploaded attachments; published result is a separate action. |

Recipient IDs are server-resolved from active role/assignment/ownership and linked case; arbitrary recipient IDs in a request body are not permission. Read, search, count, export, reply and delete/display actions use participant and case scope. Deleting a displayed letter may hide it from a mailbox but must retain immutable workflow/history and attached evidence. A letter being delivered or marked read never grants access to the underlying application or file.

On role removal, deactivation, ordinary/employer replacement or investment reassignment, revoke active case/file/memo/queue/search access immediately at the next request. Preserve earlier actor/actions and evaluation history, but do not let a stored link, message attachment, populated relation, browser cache or previously issued download URL keep access. A finalized evaluation remains attributable to its author; replacement and new-round rules determine whether it contributes to active completion. Owner exceptional replacement and reopening require reason/actor/time.

## Present implementation gaps, not target permissions

The checkout still uses multi-valued `admin`, `editor`, `representative`, `referee` roles in both [`cms-core` roles](../../packages/cms-core/src/access/roles.ts) and the [backend role type](../../apps/backend/src/auth/user-store.ts). The [dashboard router](../../apps/backend/src/dashboard/router.ts) mainly distinguishes `admin` from `representative`, with global admin list/detail access; it has no seven-role event/case assignment model. The [proxy authenticator](../../apps/backend/src/dashboard/proxy-auth.ts) accepts forwarded role values after secret validation but does not independently reload current roles. This matrix therefore cannot be used as evidence of enforcement.

[`Companies`](../../packages/cms-core/src/collections/Companies.ts) has `read: anyone`, exposing the full CMS company record rather than a public whitelist. [`Media`](../../packages/cms-core/src/collections/Media.ts) is publicly readable and stored in a public directory, so it is suitable only for editorial files. [`Users`](../../packages/cms-core/src/collections/Users/index.ts) has broad backend service-account read/update/delete and self-delete, while roles are a many-value field. Local API call sites require a specific access audit. The current request repo uses owner ID rather than company/event/subtopic/assignment; the admin queue uses `listAll`, and the [letter repo](../../apps/backend/src/dashboard/letter-repo.ts) stores attachments but lacks scoped file authorization. The admin letter route accepts a representative recipient ID, and support is limited to representative/admin. No financial package, review slot, private file store, case export or independent booth application exists yet. These are implementation tasks, not exceptions to this policy.
